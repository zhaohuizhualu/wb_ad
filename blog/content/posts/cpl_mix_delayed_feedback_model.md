## 为什么写这篇文章

微博广告 CPL（Cost Per Lead）投放体系里，有一类模型负责预估"这次广告曝光最终会不会带来付费转化"，预估分直接决定排序和出价。`cpl_mix` 就是其中之一。它和之前拆解过的 [`star_multimodal_long_seq`](/post/cpl_ctr_model_structure) 是兄弟项目，但面对一个更棘手的问题：**转化标签有延迟归因，曝光后要等约 14 天才能完全成熟**。

这带来一连串工程与建模难题：今天的样本里很多"负样本"其实只是"还没归因的正样本"；实时看到的指标和 14 天后的最终效果可能对不上；补偿机制本身又会引入偏差。本文基于 2026-11 的项目分析文档，完整梳理这个模型的业务背景、训练机制、模型结构、评估体系和下一步优化方向。

先交代三个容易混淆的口径：

- **优化目标不是"当前已归因转化"，而是 14 天最终转化概率** `P(Y_14=1|X)`，线上输出的就是这个概率；
- **当前是 PyTorch 重构版**（分支 `cpl_mix_torch`），但实际线上训练跑的是编译后的 `.so`，与 Python 源码是否完全一致需要逐次验证；
- 训练只覆盖两个优化目标（86005003、86007004），评估却包含四个——**全目标合并指标不等于训练目标的效果**。

---

## 一、业务难题：标签要等 14 天才熟

广告曝光后，用户可能立刻转化，也可能 3 天后、13 天后才转化。按业务协议，曝光约 14 天后标签才"完全归因"。这意味着任何时刻拿到手的近期样本，label 都是**删失（censored）**的：标 0 的样本里混着大量"将来会转化、只是还没回传"的假负样本。

直接把近期样本当真负样本训练，模型会系统性低估转化率——越是新鲜的流量，低估越严重。这正是整个项目设计的出发点。

---

## 二、两段式训练：day 求稳，minute 追新

解法是经典的"稳定基座 + 近期微调"两段式：

| 阶段 | 样本与作用 | 更新方式 |
| --- | --- | --- |
| day | T-14 及更早的**完全归因**样本，形成稳定基础模型 | 每天增量更新 |
| minute | 在最新 day 模型上训练 [T-13, T] 的近期样本，学习流量与转化变化 | 每 60 分钟更新 |

两个值得注意的调度细节：

1. **每轮 minute 都重新基于最新 day 模型训练近期窗口**，而不是接着上一轮 minute 续训。这避免了 minute 模型在多轮增量后漂移失控，代价是每轮重新学一遍近两周的数据。
2. 由于生产延迟，实际可用的 day 模型日期不一定严格对齐 T-14 边界，**以每轮日志记录的基础模型与样本日期为准**，不能按日历推算。

## 三、两类负采样，千万别混淆

这是整个项目里最容易踩坑的地方。系统里同时存在两种负采样，目的完全不同：

**1. 延迟归因负采样**：minute 阶段按优化目标和样本年龄，用静态配置 `guiyin_bucket.csv` 对当前负样本进一步下采样，补偿那些"还没归因的正样本"。

**2. 固定 0.05 负采样**：day/minute 都用，纯粹为降低训练成本，推理时做概率校准：

```text
p = sigmoid(z + log(0.05)) × outter_cali
```

当前 `outter_cali=1.0`。关键纪律：**不能把归因 bucket 的采样率也乘进上面的校准公式**——归因采样是在补偿未归因的正样本，不是降成本手段，两者语义不同。

### 归因负采样为什么只是近似

记最终转化概率为 p，样本年龄下已观测到的转化比例为 q。假设观测正样本概率为 pq，当前负样本以 q 保留，则采样后的正样本比例为：

```text
(pq) / (pq + q × (1 - pq)) = p / (1 + p × (1 - q))
```

在转化率很低、bucket 能准确表达归因成熟度时，这近似 p，但不是严格无偏。更重要的是：**总体正负比例接近真值，不等于每类样本的条件转化概率都准确**——广告主、行业、用户等特征都可能影响归因速度，仅按优化目标和年龄估计 q 会留下系统性偏差。

### 三个待验证的隐患

- bucket 是静态配置，动态生成 bucket 的调用当前被注释掉了；
- 样本年龄用 mapper 执行时的 `datetime.now()` 计算，而外部 label 是此前生成的快照——排队/执行延迟会造成成熟度时间不一致；
- 历史回放时必须固定 label 截止时间、年龄参考时间和随机采样条件，否则就是在"用今天的样本年龄配历史标签"。

这些目前都是待验证的优化方向，不是已证明的线上精度损失。

## 四、模型结构：PEPNET_STAR

当前配置的模型是 PEPNET_STAR，主体为 Wide + FM + Deep + PPNet 个性化门控。整体数据流：

```text
one-hot / multi-hot 特征 ID
  -> hash（保留缺失值 0）
  -> Linear 表 [5e7 × 1] / Embedding 表 [5e7 × 8] 查表
  -> multi-hot 按 slot 求和 + 有效性 mask
  -> 四条分支：
       Wide：各 slot 一阶值                       [B, 194]
       FM：二阶交叉，保留 embedding 维度            [B, 8]
       Deep：展平 1720 -> BN -> 4 层 PPNet 门控 MLP [B, 32]
       Auxiliary：5 个 slot 的 embedding 直接展平   [B, 40]
  -> concat(Wide, FM, Deep, Auxiliary)             [B, 274]
  -> 末层 PPNet GateNu，逐元素相乘
  -> Linear(274, 1) -> logits
  -> 推理时 +log(0.05) -> sigmoid × outter_cali
```

![PEPNET_STAR 模型结构](/images/pepnet_star_architecture.png)

主要超参：embedding_size=8，MLP=[128,128,128,32]，BatchNorm，Adagrad lr=0.02，单 epoch，batch_size=1024。

### PPNet 门控：容易被误读的两个细节

所有门控模块的通用上下文是 **BN 后的 Deep 输入 D**（detach 掉，只阻梯度、不冻主干），拼上 `ppnet_slot` 的个性化 embedding P：

```text
C = concat(detach(D), P)
GateNu(C, O) = 2 × sigmoid( Linear(ReLU(Linear(C))) )    # gate ∈ (0, 2)
```

主干每层：`h(i+1) = ReLU((hi ⊙ gi) @ Wi + bi)`。

细节一：配置里的 `emb_gate=[8]` **并不表示门控隐层宽度为 8**，实际宽度是 `output_dim // 2`——当前各层依次是 860、64、64、64、137。看配置望文生义会完全误解门控容量。

细节二：`detach` 只阻止门控输入 D 这条旁路的梯度，个性化特征 P 和门控参数本身正常学习。

### 当前启用与未启用

- **已启用**：Wide、FM、Deep、PPNet 中间层门控、末层门控、辅助 embedding、BN、推理负采样校准；
- **单 domain**：未配置 `domain_slot`，多域 STAR 分支未启用；
- **EPNet 未启用**：未配置 `emb_personalized_slot`；
- 序列特征是 segment sum pooling，当前没有 attention/Transformer/RNN；
- Wide 不是先求和成单个分数、FM 也不是标量——最终是拼接后统一线性映射。

一个必须反复强调的工程事实：线上训练提交的是编译后的 `.so`，不是直接跑这份 Python 源码。**任何修改都必须确认进入了编译产物**，实验要同时记录源码版本、编译包版本和 checkpoint。

## 五、评估体系：两套指标，四种口径

### 实时粗评估：只能当上线参考

每轮 minute 训练后会对下一窗口做实时评估，但此时标签远未成熟。例如某次评估 300 万样本里只有 57 个正样本——少量且**偏向快速归因**的正样本，会让实时 AUC/gap 与最终指标系统性地对不上。它只能用来抓训练事故，不能用来判断最终转化效果。

### 完全归因事后评估：等 14 天，分目标看

离线评估链路在模型之后的多个小时窗口打分，等 14 天标签成熟后以 markid 关联标签，输出**分目标**及合并的 AUC、Logloss、pctr、tctr、gap。一份历史模型的示例结果：

| 优化目标 | 正样本数 | AUC | gap |
| --- | ---: | ---: | ---: |
| 86005003 | 939 | 0.806 | +0.130 |
| 86007004 | 2000 | 0.835 | +0.306 |
| 86005005 | 82 | 0.885 | +5.855 |
| 86007001 | 2213 | 0.615 | -0.223 |
| ALL | 5234 | 0.818 | +0.137 |

这张表藏着两个重要教训：

1. **训练目标与评估目标不是同一集合**。训练只覆盖前两个目标，后两个是泛化表现；86005005 的 gap=+5.86 和 86007001 的 AUC=0.61 说明未训练目标上模型可能严重失准。必须分别报告"训练覆盖目标"、"其他目标泛化"、"全目标"三组指标。
2. **排序与校准要分开看**。不同目标的正负偏差可能在 ALL 里互相抵消；ALL 的 AUC 还混入了目标间的排序，不等于各目标内部排序能力。

### 新增的全目标评估链路 v2

为支撑上述对比，项目新增了一条独立的离线评估链路（Hadoop Streaming + TorchScript CPU 打分 + 分目标 reducer），原则是不改动原链路、不接线上训练循环。几个设计决策值得记录：

- 外部 label 文件**完全覆盖**样本 label（markid 在集合中为 1，否则为 0），不会部分回退；
- ALL 指标在合并样本上直接计算，**不是**各目标 AUC 的平均；
- 导出模型已有的 0.05 校准不重复应用；
- 已有 HDFS 结果目录直接退出而不是覆盖，空输入/异常时宁可以非零退出也不产出误导性的"成功"指标表；
- 本地有完整的无依赖测试（AUC 对照暴力 pairwise、同分、极低概率、单类别等），但真实集群冒烟尚未做。

## 六、下一步：用归因时间做监督

既然 14 天标签里藏着"A 曝光后 6 小时转化、B 曝光后 48 小时转化"这样的时间信息，能不能利用它提升最终 CVR 预估？2026-11-16 的调研给出的路线是：

**优先实验：成熟数据上的「14 天转化主任务 + 归因时间分桶辅助任务」。**

```text
L = L_14day_BCE + lambda × Y_H × L_time_bucket
```

主任务不变，线上仍输出 `P(Y_14=1|X)`；额外加一个 softmax 时间 head，预测转化条件下落入各时间桶（候选：(0,6h]、(6h,24h]、(24h,48h]、(48h,72h]、(3d,7d]、(7d,14d]）的概率，让共享表示学习"不同样本的归因速度"。A 和 B 的主任务标签都是 1，但时间监督分别落入第一桶和第三桶。

若这个实验有效，第二步才在 minute 中引入**删失似然联合建模**：把未成熟负样本当作右删失观测，似然为 `-log(1 - p(X)·F(a|X))`，而不是当成确定负样本。这对应 DFM、NoDeF、离散时间生存模型这条文献路线。

调研同时明确了几条"不建议"：

- **不能把真实归因时间作为线上输入**——曝光时它未知，直接泄漏；
- **不能仅因归因快就给正样本更高权重**——那会偏向快速转化，改变 14 天最终转化这个业务目标本身；
- **时间预测变准不必然带来 CVR 提升**——辅助任务可能负迁移，必须盯主任务效果。

工程上的前置条件也很现实：当前标签管道（`gen_markid.py` 及评估链路的 `label_window.py`）**都丢弃了时间字段**，只输出 markid；标签里的 `dt` 究竟是事件时间、回传时间还是其他口径，尚未确认。时间建模的第一步其实是先把数据契约补齐。

## 八、三个 takeaway

1. **延迟归因问题里，"负样本"是个时变概念**。今天的负样本可能是 14 天后的正样本。任何用到近期样本的设计——采样、评估、损失函数——都要先问一句：这个 label 熟了吗？把未成熟样本当确定负样本，是这个场景里最隐蔽也最常见的错误。

2. **补偿机制的每一步都要单独推导，不能叠 buff**。归因 bucket 负采样补偿未归因正样本，0.05 固定采样降训练成本，未来若上删失似然则又是一种补偿——三者语义不同，混用会重复补偿。每改一处，推理校准公式都要重新推导一遍。

3. **评估口径是这个项目的第一生产力**。"训练覆盖 2 个目标、评估看 4 个"、"实时 AUC 偏向快速归因正样本"、"ALL 的 gap 会互相抵消"——这些口径问题不厘清，任何模型改动的好坏都无从谈起。先把基线评估协议钉死（同窗口、同标签、分目标、配对比较），再谈模型优化。
